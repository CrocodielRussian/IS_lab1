# Information Security Lab #1

---

# Описание проекта

Данный проект представляет собой веб-приложение на Java/Spring, демонстрирующее практики веб-безопасности:

- JWT-аутентификация и хранение паролей в виде bcrypt-хэшей.
- Валидация входных данных и HTML-экранирование строк в ответах для снижения риска XSS.
- ORM-запросы с привязкой параметров для защиты от SQL-инъекций.
- Разграничение доступа: пользователь создаёт и получает только свои данные.
- Конфигурация через переменные окружения.

Приложение использует Java 17, Spring Boot, Spring Security, Spring Data JPA/Hibernate и PostgreSQL.
Каждая запись содержит UUID, имя (`name`), описание (`description`) и идентификатор владельца.
Владелец определяется сервером по JWT и не задаётся клиентом.

# Методы API

Базовый адрес при запуске через Docker Compose: `http://localhost:8080`.
Тела запросов и ответов передаются в формате JSON. UUID и токены ниже приведены для примера.

## 1. POST /auth/login — Аутентификация пользователя

Описание:
Метод принимает имя пользователя и пароль. При успешной аутентификации возвращает JWT-токен,
UUID и имя пользователя. Авторизация для вызова метода не требуется.

Request:

```http
POST /auth/login
Content-Type: application/json
```

```json
{
  "username": "user",
  "password": "MyStrongPassword123"
}
```

Response: `200 OK` (JSON)

```json
{
  "token": "eyJhbGciOiJIUzI1NiJ9...",
  "id": "d60ed474-8b1b-4f3c-bbe3-10a7e2eadf58",
  "username": "user"
}
```

Ошибки:

- `400 Bad Request` — некорректный JSON, отсутствующие или невалидные поля.
- `401 Unauthorized` — неверные учётные данные.

---

## 2. POST /auth/create — Регистрация пользователя

Описание:
Создаёт пользователя и возвращает JWT-токен. Имя должно быть уникальным и содержать не более
100 символов. Имя и пароль обязательны и не могут состоять только из пробелов.
Пароль ограничен 72 байтами UTF-8 из-за использования bcrypt.

Request:

```http
POST /auth/create
Content-Type: application/json
```

```json
{
  "username": "user",
  "password": "MyStrongPassword123"
}
```

Response: `201 Created` (JSON)

```json
{
  "token": "eyJhbGciOiJIUzI1NiJ9...",
  "id": "d60ed474-8b1b-4f3c-bbe3-10a7e2eadf58",
  "username": "user"
}
```

Ошибки:

- `400 Bad Request` — невалидные данные, в том числе превышение ограничения длины пароля.
- `409 Conflict` — имя пользователя уже занято.

---

## 3. GET /api/data — Получение списка своих данных

Описание:
Возвращает только записи текущего пользователя. Доступ разрешён с валидным JWT.
Если записей нет, возвращается пустой массив `[]`.

Request:

```http
GET /api/data
Authorization: Bearer <JWT>
```

Response: `200 OK` (JSON)

```json
[
  {
    "id": "59111c7d-75da-4b11-971b-504ab7f16b0e",
    "name": "Моя запись",
    "description": "Описание данных"
  }
]
```

Ошибки:

- `401 Unauthorized` — JWT отсутствует, недействителен или просрочен.

---

## 4. POST /api/data/create — Создание своих данных

Описание:
Создаёт запись с именем и описанием. Оба поля обязательны, не могут состоять только из пробелов
и ограничены 255 символами каждое. Владельцем автоматически становится авторизованный пользователь.
Передавать `id` или `userId` не нужно.

Request:

```http
POST /api/data/create
Authorization: Bearer <JWT>
Content-Type: application/json
```

```json
{
  "name": "Моя запись",
  "description": "Описание данных"
}
```

Response: `201 Created` (JSON)

```json
{
  "id": "59111c7d-75da-4b11-971b-504ab7f16b0e",
  "name": "Моя запись",
  "description": "Описание данных"
}
```

Ошибки:

- `400 Bad Request` — некорректный JSON или невалидные поля.
- `401 Unauthorized` — JWT отсутствует, недействителен или просрочен.

---

## 5. GET /api/description/{id} — Получение своей записи по UUID

Описание:
Возвращает запись, только если она принадлежит текущему пользователю.
Для чужой и несуществующей записи возвращается одинаковый код `404`.

Request:

```http
GET /api/description/59111c7d-75da-4b11-971b-504ab7f16b0e
Authorization: Bearer <JWT>
```

Response: `200 OK` (JSON)

```json
{
  "id": "59111c7d-75da-4b11-971b-504ab7f16b0e",
  "name": "Моя запись",
  "description": "Описание данных"
}
```

Ошибки:

- `400 Bad Request` — идентификатор не соответствует формату UUID.
- `401 Unauthorized` — JWT отсутствует, недействителен или просрочен.
- `404 Not Found` — запись не существует или принадлежит другому пользователю.

# Меры защиты

## Реализация аутентификации

- Пароли хранятся в виде bcrypt-хэшей.
- После регистрации или входа пользователь получает JWT в поле `token`.
- JWT подписывается алгоритмом HS256; секретный ключ передаётся через переменную окружения `JWT_SECRET`.
- Фильтр `JwtAuthFilter`, основанный на Spring Security `OncePerRequestFilter`, проверяет токен и загружает пользователя.
- Проверяются подпись, разрешённый алгоритм, issuer `lab1`, срок действия, наличие subject и существование пользователя.
- Срок действия токена по умолчанию — один час. Серверные сессии не используются.

Для доступа к защищённым методам необходимо передавать заголовок:

```http
Authorization: Bearer <JWT>
```

JWT не принимается из cookies. CSRF-защита отключена для API с явным заголовком авторизации.
При публикации приложения используйте HTTPS.

## Разграничение доступа к данным

- Идентификатор владельца при создании берётся из текущего аутентифицированного пользователя.
- Запрос списка фильтруется по идентификатору владельца.
- Запрос одной записи проверяет одновременно UUID записи и идентификатор владельца.
- Знание UUID чужой записи не даёт доступа к ней: сервер возвращает `404 Not Found`.

## Противодействие SQL Injection (SQLi)

- Используется Spring Data JPA/Hibernate с привязкой параметров запросов.
- Пользовательские строки не конкатенируются с SQL.
- Входные значения передаются как данные запроса, а не как SQL-код.

## Противодействие XSS

- Методы API возвращают JSON.
- Строки `username`, `name` и `description` HTML-экранируются через `HtmlUtils.htmlEscape` при формировании DTO.
- Например, `<script>` в ответе превращается в `&lt;script&gt;`.
- Сообщения об ошибках не отражают переданные пользователем значения.
- Валидация проверяет обязательность полей и ограничения длины; сама по себе она не заменяет экранирование.
- Клиент должен отображать строки текстовыми DOM-операциями, например `textContent`.

## Конфигурация и секреты

- Параметры подключения к БД и JWT-секрет задаются через переменные окружения.
- Локальный `.env` исключён из Git и контекста Docker-сборки.
- Контейнер приложения запускается от непривилегированного пользователя.
- PostgreSQL хранит данные в именованном томе; его порт не публикуется на хосте.

# Swagger UI

Документация доступна без авторизации:

- [Swagger UI](http://localhost:8080/swagger-ui.html).
- [OpenAPI JSON](http://localhost:8080/v3/api-docs).

Для создания своих данных через Swagger:

1. Выполните `POST /auth/create` или `POST /auth/login` через **Try it out → Execute**.
2. Скопируйте значение `token` из ответа без кавычек.
3. Нажмите **Authorize**, вставьте токен без префикса `Bearer`, подтвердите и закройте окно.
4. Выполните `POST /api/data/create`, указав `name` и `description`.
5. Получите свои записи через `GET /api/data` или одну запись через `GET /api/description/{id}`.

Если токен истёк, выполните вход повторно и замените его в **Authorize**.
При изменённом `APP_PORT` используйте этот порт вместо `8080`.

# Запуск

## Docker Compose

Для первого запуска создайте локальный файл `.env` с секретами:

```bash
cp .env.example .env
chmod 600 .env
```

Заполните `POSTGRES_PASSWORD` результатом `openssl rand -hex 32`, а `JWT_SECRET` —
результатом `openssl rand -base64 32`. Файл `.env` исключён из Git и контекста Docker-сборки.
Если `.env` уже настроен, используйте его без перезаписи.

```bash
docker compose up -d --build
docker compose ps
docker compose logs -f app
```

API доступен на `http://localhost:8080`; порт можно изменить через `APP_PORT` в `.env`.
Сеть Compose использует `172.30.10.0/24`, чтобы не зависеть от автоматического выделения
подсетей Docker. При конфликте с локальной сетью или VPN задайте свободную подсеть в `COMPOSE_SUBNET`.
Dockerfile собирает JAR на Java 17 и запускает его от непривилегированного пользователя.
Compose ждёт готовности PostgreSQL перед запуском приложения. База хранится в именованном
томе, её порт не публикуется на хосте. При повторных запусках сохраняйте пароль из `.env`:
его изменение само по себе не меняет пароль в уже созданной базе.

Остановка: `docker compose down`. Данные БД сохраняются; команда с `--volumes` удалит их.

## Без Docker

Для запуска нужен PostgreSQL. Настройки подключения и секрет JWT передаются через переменные окружения:

```bash
export SPRING_DATASOURCE_URL=jdbc:postgresql://localhost:5432/lab1
export SPRING_DATASOURCE_USERNAME=lab1
read -rsp 'Пароль БД: ' SPRING_DATASOURCE_PASSWORD
export SPRING_DATASOURCE_PASSWORD
export JWT_SECRET="$(openssl rand -base64 32)"
./mvnw spring-boot:run
```

Секрет JWT обязателен: Base64 от случайных 32 байт или больше. Не храните секреты в Git.
JWT действует один час; смена ключа делает ранее выданные токены недействительными.
Hibernate создаёт/обновляет таблицы через `ddl-auto=update`.
Пользователи и записи автоматически не создаются. Создайте пользователя через `POST /auth/create`.

Существующие записи без имени получают имя «Без названия» при обновлении схемы Hibernate.

# Проверки и CI

```bash
./mvnw clean verify
./mvnw compile spotbugs:check
./mvnw dependency-check:check
```

Интеграционные тесты используют отдельную H2-базу и создают данные перед каждым тестом; PostgreSQL для них не нужен.
Они проверяют регистрацию, повторное имя, предел пароля в байтах, вход, bcrypt, создание и чтение записей, доступность Swagger, плохие и просроченные JWT,
SQLi, экранирование XSS, валидацию и изоляцию записей пользователей. Тестовые секреты генерируются при запуске.

`.github/workflows/ci.yml` запускает на каждый push и pull request:

1. Сборку и тесты.
2. SAST: SpotBugs + Find Security Bugs, категория SECURITY. Найденные проблемы проваливают проверку. В `config/spotbugs-security.xml` исключены только информационный список эндпоинтов и чтение заголовка в JWT-фильтре, где токен проверяется криптографически.
3. SCA: OWASP Dependency-Check; CVSS >= 7 или ошибка сканера проваливают проверку.

Отчёты тестов, XML SAST и HTML/JSON SCA сохраняются как GitHub Actions artifacts, в том числе при ошибках.
Добавьте repository secret `NVD_API_KEY`, чтобы ускорить обновление базы NVD.
Без ключа сканирование тоже запускается, но может упереться в ограничения NVD (особенно в PR из fork, где secrets недоступны).
OSS Index отключён, так как требует отдельные credentials; анализ по NVD включён.
Автоматическое развёртывание не настроено: целевое окружение не задано.

Документация: [SpotBugs](https://spotbugs.github.io/spotbugs-maven-plugin/usage.html),
[Find Security Bugs](https://github.com/find-sec-bugs/find-sec-bugs),
[OWASP Dependency-Check](https://dependency-check.github.io/DependencyCheck/dependency-check-maven/configuration.html),
[JJWT](https://github.com/jwtk/jjwt).
